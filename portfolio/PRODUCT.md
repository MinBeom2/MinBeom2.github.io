## Platform

web

## Users

백엔드·SI·소프트웨어 개발 채용 담당자와 기술 면접관. 프로젝트에서 본인이 맡은 범위와 실제 구현·검증 기록을 읽고 연락할 수 있는 포트폴리오다.

## Product Purpose

김민범의 구현 경험과 문제 해결 과정을 소개한다. 홈에서 대표 프로젝트와 역할을 빠르게 확인하고, 각 프로젝트의 상세 모달에서 판단·검증·근거를 읽는다. 모달을 닫으면 읽던 홈 위치로 돌아온다.

## Operating Context

React, TypeScript, Vite의 정적 웹 사이트. GitHub 사용자 사이트 MinBeom2.github.io에 배포할 계획이다. 실제 저장소는 C:\MinBeom2.github.io, 앱은 portfolio 하위 폴더에 있다. 상세는 홈 위의 native dialog로 표시한다. 기존 해시 주소의 직접 접근·새로고침도 모달로 지원한다.

## Capabilities and Constraints

- Ait와 ONEWORK는 SSAFY 6인 팀 프로젝트다. 팀 기능과 본인 담당을 구분한다.
- SteamFolder는 개인 프로젝트이며 외부 배포 전 로컬 개발 중이다.
- nGrinder 수치는 기록된 개발·검증 조건의 결과다.
- LIKE 검색 조건을 제외한 결과는 병목 진단 대조 실험이다.
- 좋아요 총 100건 요청을 32개 작업 스레드로 실행해 최종 100개를 확인한 작업은 종료 후 개인 브랜치다. 팀 배포 미반영이다.
- ONEWORK의 localhost 요청은 수정했으며 HTTPS 혼합 콘텐츠 통합 문제는 미해결이다.
- 수상 실적은 없다. 공개 데모와 Ait 캡처는 나중에 추가할 계획이다.
- 새로운 성과·기간·운영 지표·측정 조건은 질문과 근거 없이 작성하지 않는다.

## Brand Commitments

화면 문구와 메타 설명에 중간 점을 사용하지 않는다. 나열은 쉼표로, 문장 연결은 자연스러운 조사와 접속어로 표현한다.

사용자가 밝은 회색 바탕과 차콜 글자의 모던한 방향을 선택했다. 코드로 구현하고 실제 화면에서 검토한다. 실제 프로젝트 로고의 원래 색상을 임의로 바꾸지 않는다. 2026-10-14 사용자 요청에 따라 헤더는 이름·로고·연락 버튼을 제거하고 프로젝트·작업 방식·소개만 중앙의 어두운 아일랜드에 배치한다. 스크롤 위치에 따라 메뉴를 강조하고, 프로젝트 상세는 새 페이지 대신 모달로 연다.

2026-10-16 표시한 스크린샷에 따라 홈의 Ait 검증 카드, 프로젝트 살펴보기·GitHub 버튼, 주 사용 기술 목록과 소개의 GitHub 링크를 제거한다. 프로젝트 목록은 세 프로젝트 모두 같은 크기의 작은 정사각 타일에 로고·이름만 표시한다. 클릭하면 기존 상세 모달이 확대되어 열린다. SteamFolder의 제공된 로고가 없어 기존 아이콘 체계의 중립 폴더 아이콘으로 표시하며 공식 로고를 만들지 않는다.

후속 디자인 확인에서 사용자는 큰 소개 문구를 유지하되 소개와 프로젝트를 더 가깝게 배치하고, 홈·기술 목록·프로젝트 상세의 간격과 위계를 함께 정돈하는 방향을 선택했다. 기존 삭제 항목과 정사각 타일, 기술의 예시 등급·근거 펼침 방식은 유지한다.

이후 사용자는 첫 소개를 더 크게 보여주고 프로젝트가 첫 화면 아래로 내려가도록 요청했다. 데스크톱과 모바일 모두 첫 화면을 소개로 채우는 방향을 확인했으며, 이 요청이 앞선 소개 밀도 선택을 대체한다. 제목은 두 줄을 유지하고 프로젝트는 스크롤하거나 상단 메뉴로 이동해 확인한다.

## 2026-10-17 화면 비중 조정 승인

사용자는 배포 화면의 소개 여백과 낮은 프로젝트·작업 방식 영역을 지적한 뒤 다음 방향의 구현을 승인했다. 첫 소개는 화면 전체 높이와 두 줄 제목을 유지하되 큰 화면의 제목 최대 크기를 96px로 확대한다. 프로젝트는 제목 아래 기존 로고·이름만의 정사각 타일 세 개를 배치한다. 작업 방식에는 개인 검증 환경의 nGrinder 전후 기록, 채팅 권한 확인 흐름, 실제 Git 가이드 일부와 상세 근거 링크를 둔다. 모바일에는 고정 섹션 높이를 강제하지 않는다.

이는 앞선 프로젝트 제목·타일의 좌우 배치와 80px 최대 제목을 대체하는 최신 승인이다. 회색·차콜, 기존 글꼴, 실제 로고와 사진, 모달 동작과 사실의 검증 범위는 유지한다.

## 2026-10-18 AI 활용 역량

사용자는 AI와 함께 개발하는 방식과 SteamFolder의 AI 연동 기능을 포트폴리오에 추가해 달라고 요청했다. 홈의 작업 방식 아래에는 작성된 코드의 흐름 파악, 더 단순한 구현 판단, 변경 파일과 스테이징 검토를 둔다. 비밀정보 파일 사례는 사용자가 선택한 대로 일반적인 검토 습관으로 요약한다. 구체적인 파일명과 사건 경위는 공개하지 않는다.

SteamFolder 상세에는 피드백을 MySQL에 먼저 저장하고 커밋 후 비동기로 AI가 P0, P1, P2를 분류하는 구현을 소개한다. P0는 분석 완료 후 즉시, P1과 P2는 한국 시간 오전 9시에 Discord Webhook으로 전달한다. 로컬 코드와 사용자 설명을 함께 근거로 사용한다. 아직 수행하지 않은 장애 검증이나 분류 정확도·시간 절감 효과를 실적으로 쓰지 않는다. 이번 작업은 로컬 수정이며 push는 사용자의 명시적인 요청이 있을 때만 수행한다.

## 2026-10-18 프로젝트 기술 선택과 대안

사용자 인터뷰 Q1–Q4와 코드 확인을 바탕으로 상세의 기술 적용을 기술 선택과 이유로 확장했다. Ait는 개발 막바지의 구현 부담을 고려한 SSE 선택, ONEWORK는 실제 CCTV와 유사한 RTSP 중계 및 낮은 지연을 목표로 한 MediaMTX/WebRTC, SteamFolder는 향후 여러 서버가 요청 제한 상태를 공유하도록 선택한 Redis를 설명한다. 현재 구조의 대안 비교를 당시의 실험이나 기억나지 않는 검토 경험으로 제시하지 않는다.

Ait의 알림 수신 문제는 별도의 해결 사례로 분리한다. Vercel 배포 후 수신 문제, 8초 heartbeat와 emitter 정리, 변경 후 수신 확인을 기록한다. Function 최대 실행시간이 heartbeat로 해제된다는 주장은 하지 않는다. ONEWORK의 WebGL은 같은 페이지의 HTML 영상 오버레이이며, MediaMTX 중계와 WebRTC/HLS 재생 비교를 구분한다. 영상 지연 미측정과 HTTPS 혼합 콘텐츠 미해결 상태를 보존한다. SteamFolder는 로컬 단일 서버 개발 중이며 실제 다중 서버의 요청 제한 검증은 아직 하지 않았다.


## 2026-10-18 ONEWORK 중계 서버 대안 보강

사용자가 제공한 설명과 실제 webcam_streamer.py, mediamtx.yml, Compose, WebGL 호출·재생 코드를 바탕으로 MediaMTX의 프로젝트 적합성을 보강한다. RTSP 입력과 WebRTC 출력 연결, 별도 런타임 의존성이 없는 실행 파일 및 실제 Docker/YAML 구성, 설비별 경로와 fMP4 녹화, 낮은 지연을 목표로 한 WebRTC 재생을 구분한다. FFmpeg는 H.264 인코딩, MediaMTX는 중계, 브라우저는 최종 재생을 맡는다.

현재 구조의 중계 서버 대안으로 go2rtc, Janus Gateway, OvenMediaEngine를 공식 문서에 근거해 비교한다. 당시 모두 구현·측정한 비교로 표현하지 않으며, MediaMTX의 서버 간 지연 우위를 주장하지 않는다. 기존 WebRTC/HLS 비교는 재생 방식으로 별도 보존하고, 영상 지연 미측정 및 HTTPS 연동 미해결 상태도 유지한다.
